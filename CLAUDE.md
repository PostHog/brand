# CLAUDE.md

`@posthog/brand` — an npm library that bundles PostHog's brand assets (hedgehog
illustrations, logos, crests, and brand colors) as React components, raw SVGs, PNG
URLs, and color tokens. Fully offline; no runtime CDN.

## Data flow

```
Figma brand book  --sync.ts-->  assets/<namespace>/  --codegen.ts-->  src/generated/  --tsdown-->  dist/
```

- **`scripts/sync.ts`** — the only networked script. Walks the configured Figma pages
  (`scripts/lib/figma-pages.ts`), renders every component to BOTH an optimized inline SVG
  (SVGO, `scripts/lib/svg.ts`) and an optimized PNG (pngquant palette-quantization + oxipng
  lossless recompress, `scripts/lib/png.ts`) via the Figma API, and writes `assets/`.
  Incremental: re-renders only assets whose Figma node subtree hash
  changed since the last sync. Needs `FIGMA_TOKEN` (a Dev/Full-seat PAT — Viewer seats are
  ~6 req/month). Run with `pnpm sync` (`--force` re-renders all, `--check` reports drift).
  Colors are NOT synced — they are a fixed, hand-maintained palette in `static/colors.ts`.
- **`scripts/lib/figma.ts`** — rate-limit-aware Figma REST client (serialized, spaced by
  `FIGMA_MIN_INTERVAL_MS`, backoff on 429/5xx, batched `/images` renders). Only the API
  endpoints are metered; downloading rendered S3 assets is free.
- **`assets/`** — committed source of truth for illustrations: `<namespace>/catalog.json`,
  `<namespace>/vectors/*.svg`, `<namespace>/png/*.png`, and `sync-state.json` (keyed
  `<namespace>/<slug>`).
- **`static/colors.ts`** — the hardcoded brand palette (`BrandColors`), hand-maintained
  source of truth for colors. Edit a value here (and commit a changeset) to change the
  published palette; `codegen.ts` reads it.
- **`scripts/codegen.ts`** — pure transform of `assets/` + `static/colors.ts` (+ package.json's
  version) → `src/generated/`. Gitignored output; regenerated by `prebuild`/`pretest`. Run with
  `pnpm codegen`. Applies the rename overrides in `scripts/lib/renames.ts` (see
  Conventions) as it emits.
- **`assets/releases.json`** (`scripts/lib/releases.ts`) — the release ledger: each published
  version's release date, and the version that first shipped each asset (keyed like
  `sync-state.json`, by raw Figma slug, plus the Figma node id so a Figma rename keeps its
  `since`; a removed asset is dropped, so a re-added one counts from its return). Written ONLY
  by `scripts/stamp-release.ts`, which `release.yml` runs right after `changeset version` and
  before `pnpm build`, committing it with the bump; codegen turns it into `AssetMeta.since`
  (`{ version, date }`, absent for an asset synced since the last release) and the root
  `release` export (package.json's version + date — codegen throws if that version isn't
  stamped). History before the ledger was backfilled from the tagged releases' catalogs and npm
  publish dates; hand-edit it if an old `since` is wrong.
- **`scripts/lib/renames.ts`** — manual slug/name overrides for assets whose Figma-derived
  names read poorly. A presentation layer applied at codegen time, offline.
- **`src/`** — handwritten runtime + entry points; `src/generated/` is machine-written.
- **`src/logo/`** — the `<Logo>` component (`./logo` export). NOT Figma-synced or codegen'd:
  the logo is a small, stable mark, so its SVG geometry is inlined in `src/logo/geometry.ts`
  and exposed as one generic, parametric compound component (`variant`/`layout`/`color`,
  plus `Logo.Logomark`/`Logo.Wordmark`). Hand-maintained — edit it directly (with a changeset).
  Unlike the rest of the repo (PolyForm Strict), the logo is used under the logo usage
  guidelines (`LOGO_USAGE_GUIDELINES` in `site/src/logo-files.ts`, shown at
  `LOGO_GUIDELINES_URL` in `site/src/agent-paths.ts`). The scope section at the top of `LICENSE`
  lists the logo paths and links the guidelines; the README must agree with both.
- **`src/fonts/`** — RoundHog, the brand typeface (`./fonts` + `./fonts/css` exports). NOT
  Figma-synced or codegen'd: the eight `woff2` faces live in `assets/fonts/*.woff2` (committed,
  hand-maintained) and are copied by `tsdown` to `dist/fonts/` next to the font modules, so the
  `new URL("./RoundHog*.woff2", import.meta.url)` refs in `src/fonts/roundhog.ts` resolve the
  same way the PNGs do. `./fonts` exports the face metadata + per-face URLs; `./fonts/css`
  exports a ready-to-inject `@font-face` string; `./fonts/*` exposes the raw woff2 by subpath.
  Each face is also cut by script into subsets with non-overlapping `unicode-range`s (latin,
  latin-ext, greek, cyrillic, rest — `SUBSET_TARGETS` in `scripts/lib/fonts.ts`) in
  `assets/fonts/subsets/`; `roundHogFontFaceCss` registers those instead of the full face, so a
  page loads only the scripts it shows and never the full file. `pnpm fonts:subset` writes them
  and the committed `src/fonts/subsets.ts` (their URLs + ranges; don't hand-edit). To
  change/add faces, drop the woff2 in `assets/fonts/`, run `pnpm fonts:subset`, and edit
  `src/fonts/` (with a changeset). `tests/fonts.test.ts` fails if a subset or its range is stale.

## Conventions

- Namespaces: `hoggies`, `crests` (Figma-synced illustrations) + `colors` (data) + the
  handwritten `logo` (see `src/logo/`). The synced namespaces are defined in `src/types.ts`
  (`NAMESPACES`) and mapped to Figma pages in `scripts/lib/figma-pages.ts`; `logo` is neither.
- Component name carries the family word + PascalCase(slug): hoggies prefix it
  (`Hedgehog<Name>`); crests append it (`<Name>Crest`) so the name reads the
  same in every crest export. SVG string export = lowerFirst(component)+`Svg`, PNG URL
  export = lowerFirst(component)+`Png` (e.g. `marketingCrestSvg`, `hedgehogDirectorPng`).
- **Crest tiers**: crests come in two sizes — `full` and `mini` — keyed off the Figma
  `Property 1` variant (`figma-pages.ts` `tierVariantProp`) and lifted into `AssetMeta.tier`
  rather than the slug. Each tier is its own **export group** (`ASSET_GROUPS` in `types.ts`):
  a subpath (`crests/full`, `crests/mini`), a generated dir (`src/generated/crests/<tier>/`),
  and on-disk sources under `assets/crests/<tier>/{vectors,png}/`. Both tiers share one
  `assets/crests/catalog.json`, so a crest slug is unique only within a (namespace, tier).
  Minis keep a trailing `Mini` in their identifiers (`MarketingCrestMini`, `marketingCrestMiniSvg`).
  The combined `@posthog/brand/crests` barrel (`src/generated/crests/index.ts`, one
  `src/generated/crests/<slug>.tsx` per slug) re-exposes them as a **compound component**
  `<Name>Crest` — base is the full illustration, `.Mini` (when a mini exists) is the badge,
  attached via `Object.assign`. `writeCombinedCrests` in `codegen.ts` emits it after the
  group loop; the tier-specific `crests/full` + `crests/mini` barrels are unaffected.
- Every asset ships as BOTH svg and png — there is no per-asset `delivery` field.
- `COMPONENT_SET` variants are flattened to one asset per variant; duplicate names get a
  `-2` suffix (`dedupeSlugs`, applied per tier). SVG ids are prefixed `<namespace>-<slug>-`
  so inlined assets never collide.
- **Renames** (`scripts/lib/renames.ts`): a global `RENAMES` map (`namespace` → original
  `slug` → `{ slug?, name? }`) gives poorly-named assets a better slug and/or display name —
  e.g. `9-9-6` → `996`. Applied by `codegen` (read
  inputs by the Figma slug, emit every module/identifier/export/`AssetMeta` by the renamed
  one); the committed `assets/` mirror keeps the raw Figma slug, so `sync` never reconciles
  hand-edits. Offline (`pnpm codegen`); changes the public API, so commit a changeset with it.
- **Variant families** (`scripts/lib/variants.ts`): a numbered family (`noir-1` … `noir-5`)
  ships as ONE compound component taking a `variant` prop — `<HedgehogNoir variant="5" />`,
  keys are strings — instead of `HedgehogNoir1` … `HedgehogNoir5`. Grouping is **inferred**
  (`inferVariants`), never hand-listed: any published slug ending in `-<digits>` is that
  variant of the base slug before it, ordered numerically with the lowest as the default.
  The one exception is when the bare base slug also exists — that's a `dedupeSlugs`
  artifact, not a family, so it stays standalone. Inference runs on _published_ slugs, so
  renames apply first (which is how `9-9-6` → `996` avoids reading as variant `6` of
  `9-9`), and per export group, since slugs are unique per (namespace, tier). Members keep
  their own svg/png/meta modules + `AssetMeta` (with `variant: { variant: "<key>" }`) under
  `<base>-<key>`; only the standalone component is replaced.
- `tsc` runs with `isolatedDeclarations` — every generated export needs an explicit type.
- Exports are fully namespaced with no back-compat, one family per export group `<g>`
  (`<g>` is `hoggies`, `crests/full`, or `crests/mini`): `./<g>`, `./<g>/svg[/*]`,
  `./<g>/png[/*]`, `./<g>/metadata`, plus `./crests` (combined compound barrel), `./logo`
  (the standalone `<Logo>` component — no svg/png/metadata subpaths), `./colors` (tokens plus
  `colorCssVariable(slug, tone?)`, which codegen also uses to name the `colorsCss` properties —
  `src/color-variables.ts`, kept free of generated imports for that reason), and `./colors/css`. Root `.` is React-free and image-free: types, the cross-namespace
  `allAssets` manifest (`src/generated/manifest.ts`, the union of every group's
  `manifest.ts`), `release` (`src/generated/release.ts`), and the search helpers `findAssets`/`getAsset`/`getVariants` (a numbered
  family's members, in variant order)/`getComponentName` (`src/search.ts`) — safe to import when building an asset picker without pulling in any
  component or payload.

## Releases

No PRs — everything is committed directly to `main` (verified API commits via the
Releaser GitHub App). Daily `sync.yml` (needs the `FIGMA_TOKEN` secret) commits new assets +
a changeset to `main` through `scripts/commit-to-main.ts` (GraphQL `createCommitOnBranch`,
split into several commits when a big re-render would exceed GitHub's 45 MB request cap;
deletions, catalogs, `sync-state.json` and the changeset go in the last one, so every commit
builds and the release fires once); that triggers `release.yml`, which (gated by the `Release`
environment + Slack approval, per the PostHog SDK handbook) runs `changeset version`, commits
the bump to `main`, and publishes to npm via trusted publishing (OIDC). Publishing
`@posthog/brand` requires the npm trusted-publishing config to be set up for that package name.

## Demo site

`site/` is a Vite + React SPA that showcases the whole package (overview, logo, colors, hoggies,
crests), plus the "Built with PostHog" website badges (`/badges`, below). The repo is a pnpm workspace (`pnpm-workspace.yaml`); `site/` is a separate private
package (`@posthog/brand-site`) that depends on `@posthog/brand` via `workspace:*` and imports it
through the real `exports` map (→ `dist/`), so it doubles as an integration test of the published
surface. Because of that, the lib must be built first: `pnpm dev:site` / `pnpm build:site`
(root scripts) run `pnpm build` then the site. The asset grids render the package's **bundled
PNG thumbnails** resolved by slug (`getComponentName` → the `…Png` URL export in a namespace
import of the png barrel — `site/src/assets-hoggies.ts`, `assets-crests.ts`), each `<img>`
fixed-height + `loading="lazy"` so only on-screen tiles fetch their (separately emitted) PNG
file. Rendering inline SVG instead would inline every asset's full-detail SVG body into one
route chunk — hoggies alone was ~27 MiB, over Cloudflare Pages' 25 MiB per-file cap; PNGs keep
the JS tiny and never bundle the payload. (Vite still inlines the sub-4 KB mini-crest PNGs as
data URIs into the crests route chunk rather than emitting files.) Each tile does a blur-up:
the `brandLqip()` Vite plugin (`site/lqip-plugin.ts`, dev-dep `sharp`) reads those same `dist/`
PNGs at build time, downscales each to a ~20px blurred WebP, and serves them as
`virtual:brand-lqip/<group>` maps (keyed by the same PNG export name) inlined as data URIs —
so a tiny placeholder paints instantly behind each `<img>` and fades out on load. Clicking a
tile (`useAssetCopy`, `site/src/components/CopyMenu.tsx`) copies just the PNG (`image/png`);
right-click opens a menu (import / SVG as text / SVG as `image/svg+xml` / PNG / Download PNG,
saved as the tile's `fileName`, e.g. `posthog-crest-marketing-mini.png`); the outcome is
flashed over the tile by the shared `CopyFlash` (`site/src/components/CopyFlash.tsx`). The click is
PNG-only on purpose: an item that also carries the import line as `text/plain` gets pasted
as both by Slack (image attached, text in the message box). Payloads go in as promises
because Safari only allows the write synchronously inside the gesture. The SVG comes from `brandSvg()` (`site/svg-plugin.ts`),
which serves `virtual:brand-svg/<group>` maps of one lazy `import("@posthog/brand/<g>/svg/<slug>")`
per asset (its own chunk, fetched on copy). The loaders rebuild the markup from the leaf's
`viewBox` + `body` (byte-identical to its `svg` export) instead of reading `svg`, because the
leaves the Overview/404 import statically sit in the entry chunk, and asking for their
duplicated `svg` string there adds ~1.4 MB. The Logo page follows the brand handbook
(posthog.com/handbook/brand/assets): preset cards for its approved versions (each with when to
use it), the do's/don'ts, then a builder (layout / variant — the presets' full color, print,
black, or white / canvas) for anything the presets don't cover, then the React API. Its logos copy the same way
(click = PNG, right-click = menu, same `CopyFlash`), but the logo ships no svg/png
exports, so `site/src/svg-export.ts` snapshots the rendered `<svg>` (currentColor resolved,
viewBox grown to its bbox, optionally padded to a square/circle-safe canvas for avatar uploads)
and rasterizes the PNG in a canvas — at 1x/2x/4x (400/800/1600px on the long side), picked
per row in the menu, with a plain click copying 2x; the menu adds "Copy JSX" there. The heavy
catalog routes are also `React.lazy` code-split so the initial bundle stays small. Because a
lazy chunk that 404s (a tab holding a pre-deploy `index.html`) would otherwise unmount the
whole app to a blank page, the routes sit inside an `ErrorBoundary`
(`site/src/components/ErrorBoundary.tsx`, keyed on the pathname so navigating clears the
error) and `main.tsx` reloads once on Vite's `vite:preloadError`; unmatched paths get a `*`
404 route rather than an empty `<main>`. The `Suspense` boundary sits _outside_ that keyed
`ErrorBoundary`: React Router runs navigations as transitions, which keep the current page on
screen while the next chunk loads only if the boundary survives the navigation — nested inside
the keyed one it remounted every click and flashed its fallback. Nav links also warm their
chunk on hover/focus (`site/src/prefetch.ts`), and `main.tsx` skips its reload while such a
speculative prefetch is in flight. The footer shows the
package `release` the site was built from, and each detail page lists its asset's facts
(`site/src/components/AssetFacts.tsx`: component, slug, the release that first shipped it,
tags collapsed in a `<details>` that find-in-page still opens; `site/src/release.ts`; a variant family or a crest's two tiers count from the oldest member,
also in `catalog.json` and the markdown twins); hoggie grid tiles get a "New" badge for 30 days
after the release that first shipped them (`isNew`, checked against the visitor's clock so it
expires without a redeploy). The site is
themed from the package's own `colorsCss` tokens and styled after posthog.com (`site/src/theme.css`:
frosted translucent nav/page panels over posthog.com's keyboard-garden wallpaper — its grass
(`site/src/assets/garden-grass.webp`, `garden-grass-mobile.webp` at ≤640px) and origami hogs
(`site/src/assets/origami-garden.webp`) — its raised 3D
buttons and callout boxes; solid surfaces under `prefers-reduced-transparency`). `<CodeBlock>`
highlights its TSX with `sugar-high` (colors are the `--sh-*` properties in theme.css); keep
trailing `//` comments in a snippet aligned to one column. Because `@posthog/brand` is consumed through
a workspace symlink, its bare `react` imports resolve from the repo root (which installs its own
React for the library's tests), so `vite.config.ts` sets `resolve.dedupe: ["react", "react-dom"]`
— without it the bundle carries two React instances and every route rendering a hook-using
export (e.g. `<Logo.Logomark>`) dies on a null dispatcher. CI builds the site and asserts the
bundle contains exactly one React copy. It is NOT published to
npm; it deploys to Cloudflare Pages via the dashboard's Git integration (root dir = repo root,
build = `pnpm build:site`, output = `site/dist`). Node is pinned via `.nvmrc` (≥22.18):
the build runs the `.ts` scripts in `scripts/` directly through Node's native TS
type-stripping, which is only on-by-default from Node 22.18/23.6 — older Node throws
`ERR_UNKNOWN_FILE_EXTENSION` on `codegen.ts`.

**Icons + social card**: `site/scripts/gen-brand-icons.ts` (`pnpm gen:site-icons`) rasterizes
the favicon set (`favicon.svg`/`.ico`/`-96x96.png`, `apple-touch-icon`, the manifest's
`icon-{192,512}` + maskable) **from the repo's own sources** — the `<Logo>` geometry in
`src/logo/geometry.ts` — through the same renderer as the published `/logo/*` files
(`site/agent/logo-render.ts`, `logoArtSvg` + `rasterizeSvg`). Output is committed to `site/public/` (not built on deploy: it changes ~never, and the dev server needs it). The social card `site/public/og.png` (also the README banner) is NOT generated: it
is a designed 1920x1080 illustration, committed as-is (downscaled from the design export and
palette-quantized). To replace it, overwrite the file and update `og:image:width`/`height` in
`site/seo-plugin.ts` and `OG_IMAGE_ALT` in `site/src/seo.ts` if they change.

**SEO/AEO**: `site/seo-plugin.ts` (`brandSeo()`) owns everything a crawler sees, driven by the
one page table in `site/src/seo.ts` (`PAGES`) that the runtime `useSeo` hook
(`site/src/useSeo.ts`, called by each page) also reads, so served HTML and client-side
navigation can't drift. `transformIndexHtml` replaces the `<!--seo-->` marker in `index.html`
with the head block (title/description/canonical/icons/OG/Twitter/JSON-LD), delimited by
`<!--seo:start-->`/`<!--seo:end-->`; `closeBundle` then stamps one static file per route
(`dist/logo.html`, …) by swapping that block and filling `#root` with a plain-HTML copy of the
page (headline, lede, internal links, and the full asset list on the catalog routes) — because
answer-engine crawlers and social unfurlers don't run JS, and `main.tsx` clears `#root` before
`createRoot`. The JSON-LD `Organization` node is a verbatim copy of posthog.com's shared
`POSTHOG_ORGANIZATION` (`src/components/seo.tsx` there) and carries **its** `@id`
(`https://posthog.com/#organization`), so both sites resolve to one entity rather than two
drifting descriptions of PostHog — re-sync it if posthog.com's changes. Asset detail pages
are prerendered too — one `dist/crests/<slug>.html` per crest and `dist/hoggies/<slug>.html`
per hoggie (a variant family is one page), from `crestPageSeo`/`hoggiePageSeo` in `seo.ts`,
which `CrestDetailPage`/`HoggieDetailPage` also call — each with the asset's own PNG as its
share image, an `ImageObject` JSON-LD node, and a three-level breadcrumb — plus `404.html`
(same shell, `noindex`, no canonical) and `sitemap.xml` (with Google image entries). Every
page's head carries `<link rel="alternate" type="text/markdown">` to its markdown twin. The
`/badges` shell also lists each badge with its embed code and the usage terms (`Route.badges`).

**Agents** (`site/agent-plugin.ts`, `site/agent/`): the build also publishes, from one
catalog (`agent/data.ts`, read straight from the package's built `dist/` leaf modules):
every asset as a static file at a stable, unhashed URL — `/hoggies/<slug>[-<variant>].svg|png`,
`/crests/<slug>[-mini].svg|png`, `/logo/<id>.svg|png` (rendered by `agent/logo-render.ts` from
`src/logo/geometry.ts`; the file set is `site/src/logo-files.ts`, which the Logo page's presets
also render from), `/badges/<id>.svg|png` (below), `/fonts/*.woff2` + `roundhog.css`,
`/colors.json|css` — plus the markdown
twin of every page (`/logo.md`, `/hoggies/chart.md`, `/` → `/index.md`; the prose is plain
markdown in `site/agent/pages/` with `{{placeholders}}` that `agent/markdown.ts` fills with the
data-driven tables/lists — edit the `.md`, not the TS),
`/llms.txt`, `/llms-full.txt` and `/catalog.json`. URL shapes live in `site/src/agent-paths.ts`
so docs and links can't drift from what's served. The docs lead with "install
`@posthog/brand`" and treat downloads as the fallback for non-JS use. `pnpm dev` serves the same
files from memory. **WebMCP**: `site/src/webmcp.ts` registers tools on `document.modelContext`
(definitions in `webmcp-tools.ts`, also listed in `index.md`) that answer from `/catalog.json`. Chrome only exposes `document.modelContext` behind a flag
or the WebMCP origin trial: set the (public, origin-bound) trial token as the build-time env var
`WEBMCP_ORIGIN_TRIAL_TOKEN` (committed in `site/.env.production`, expires 2027-03-30; a Cloudflare Pages env var overrides it) and the `originTrials` plugin (`site/origin-trial-plugin.ts`) emits
`<meta http-equiv="origin-trial">` on every page; unset, no tag.

**MCP server** (`/mcp`, `edge/` + `functions/`): a remote MCP server (Streamable HTTP, stateless,
JSON responses, no auth) for agents that don't browse the site. `functions/mcp.ts` is the Cloudflare
Pages Function route (Pages builds every file under `functions/` into a route, so it only imports
`edge/src/mcp.ts`, where the server lives; `edge/` is a private workspace package holding the
server's dependencies). Its tools are `MCP_TOOL_DEFINITIONS` in `site/src/webmcp-tools.ts` (the
WebMCP asset tools plus `get_brand_asset_file`, which returns an SVG as markup and a PNG as image
content) and they answer with `site/src/brand-tools.ts`, the same code as the WebMCP tools, from
`/catalog.json` and the asset files read through the Pages `ASSETS` binding. The asset tools'
shared logic lives in `brand-tools.ts` (pure: no DOM, no fetching) for that reason, and the docs
list the MCP tools from the same table (`{{mcpTools}}` in `agent/pages/index.md`). Calls are
captured as `$mcp_tool_call` by `@posthog/mcp` (`instrument`, with the injected `context` intent)
into posthog.com's project (`site/src/posthog-project.ts`), except from localhost; set the
`POSTHOG_HOST` binding to send them to a local sink instead. `edge/` typechecks with the site's
compiler settings (it imports site modules) and minimal hand-written Cloudflare types. Run it with
`pnpm dev:edge` (builds the site, then `wrangler pages dev site/dist --service IMAGE_MAKERS=brand-image-makers` on :8788) and check it with
`node edge/scripts/smoke.ts [url]`, which calls every tool with the official MCP client (point it
at `https://brand.posthog.com/mcp` after a deploy).

**Image makers on the server** (`/tools/images/<maker>.png?image=…`, and the MCP `make_*_image`
tools): agents that don't browse get real images from the makers. A saved image's PNG is its maker
link plus `.png` (`/tools/images/blog?image=X` → `/tools/images/blog.png?image=X`). The makers only
draw in a browser (canvas, fonts, images), so a headless one runs them: the image makers Worker
(`edge/src/image-makers-worker.ts`, its own `edge/wrangler.jsonc`; needs Workers Paid with Browser
Run) opens the headless image makers page (`site/image-makers-headless.html` →
`site/src/image-maker/headless.ts`, a second Vite entry with no React or analytics that registers
RoundHog like `main.tsx`, served at `/image-makers-headless`) and calls `window.brandImageMakers`,
which is `exportPng`/`makeImage` in `site/src/image-maker/agent.ts`, i.e. the makers' own code.
`exportPng` opens an `?image=` value the way the maker opens a link (its settings over the maker's
`blank()`), waits for the same images and fonts, and draws at full size like `downloadPng`, so an
export is the maker's download: in one browser build it is pixel-identical (checked against every
`site/tests/makers/` case, with the GPU off on both sides; the GPU path anti-aliases a little
differently, as machines already do). The Worker has no public URL: `functions/tools/images/[file].ts`
forwards `.png` requests to it (and passes the maker pages and their `.md` twins on to the static
files with `next()`), and the MCP server calls its `POST /make`, both through the Pages project's
`IMAGE_MAKERS` service binding (set in the Pages dashboard; without it the PNG URLs answer 503 and
the MCP server lists no image tools). It reuses idle browser sessions (`keep_alive` 60 s), caches
each PNG for a day by normalized URL, rate limits uncached work per client IP
(`IMAGE_MAKERS_LIMIT`), caps saved images at 16 KB, and only loads pictures from the site,
`PICTURE_HOSTS` (res.cloudinary.com, posthog.com) and `data:` URLs: `disallowedPicture` rejects the
rest up front, and the session's Browser Run `guardrails` block them at the network (local runs
don't enforce guardrails). It deploys through Cloudflare Workers Builds: the `brand-image-makers`
Workers project is connected to this repo with root directory `edge` (its `pnpm install` installs
the whole workspace, and wrangler bundles the one site module it imports), the default deploy
command `npx wrangler deploy`, build watch paths `edge/*` and `site/src/image-maker/catalog.ts`
(other changes skip the build; the headless page ships with the site), and preview builds off. The
project's name must match `name` in `wrangler.jsonc`; `pnpm --filter @posthog/brand-edge
deploy:image-makers` deploys by hand. Run it all locally: `pnpm dev:edge` (site + functions on
:8788) and `pnpm --filter @posthog/brand-edge dev:image-makers` (the Worker on :8790, with a local
Browser Run Chrome, using the :8788 site); the smoke test then covers the image tools too.

**Website badges** (`/badges`): two "Built with PostHog" badges (a light and a dark plate) that
other sites hotlink from `/badges/<id>.svg` (100×50, PNG 300×150). One table,
`site/src/badge-files.ts`, holds the badges, their embed code (HTML and Markdown, linking
`posthog.com/?utm_source=badge&utm_medium=referral&utm_content=<id>`) and the usage terms, and
feeds the page, the markdown, the shell, `catalog.json` (`badges[]`) and WebMCP (`type: "badge"`).
`agent/badge-render.ts` draws each one from the landscape lockup in `src/logo/geometry.ts` and the
"Built with" lettering in `site/src/badge-text.ts`. Shown through `<img>` on other sites, a badge
can't load a font, so the lettering is a RoundHog outline that `node scripts/gen-badge-text.ts`
writes (harfbuzzjs + fontverter, `scripts/lib/outline.ts`); `tests/badge-text.test.ts` fails if
it is stale. The renderer prefixes the logo's ids per badge and throws if a file isn't
self-contained (`<text>`, `<style>`, `href=`, `currentColor`…). The logo's clear space (the "P"
height, 9.44 px at 80 px wide) sets the layout, so keep it when changing sizes. The site footer shows the light
badge (from its static file) linking to `/badges`; in the top nav it sits under Tools.

**Marketing assets** (`/marketing-assets`, under Brand kit): finished, designed raster images from the brand
book's "hero images" Figma page: 4 product heroes, each in two formats (`MarketingAssetGroup.formats`:
16:11, 1600×1100 frames → 3200×2200 PNG at `<id>.png`, and 16:9, 1600×900 → 3200×1800 at `<id>-16x9.png`; 2x matches the
garden art inside; the page previews the first format and has one download button per format) and 10 App Store screenshots (440×956 → 1320×2868, the App Store's 6.9" iPhone
size). The page is kept short on purpose: one line (missing something → the Graphics team), then
one sideways-scrolling row per kind; what each kind is for and how to use it is only in the
markdown twin and the prerendered shell. NOT Figma-synced or in the npm package: one table,
`site/src/marketing-assets.ts` (frame node ids, render scale, copy), feeds the page, the shell, the
sitemap, the markdown (`agent/pages/marketing-assets.md`), llms.txt and `catalog.json` (`marketingAssets[]`).
The files are committed to `site/public/marketing-assets/` (lossless PNG, ~39 MB, plus the page's WebP
`previews/`), written by `FIGMA_TOKEN=… pnpm fetch:marketing-assets` (`site/scripts/fetch-marketing-assets.ts`,
which fails if a frame changed size). Re-run it when the Figma page changes, but only commit the files
whose design actually changed: every Figma render differs from the last by a little noise. The page's backgrounds
(core and garden) are left out on purpose.

**Top nav** (`NAV` in `site/src/App.tsx`): Logo · Hoggies · Brand kit ▾ (Crests, Colors, Fonts, Marketing assets) ·
Tools ▾ (Image makers, each maker from `catalog.ts`, Website badges); the brand mark links home, so
there's no Overview item. A group is a `NavMenu` (`site/src/components/NavMenu.tsx`): a button
opening a panel of links, which closes on Escape, an outside click, focus leaving it or a followed
link. Below 620px the links take a row under the logo and a group's panel spans the taskbar.

**Image makers** (`/tools/images`, in the top nav under Tools): the team's image makers. This
site is their only source (the Claude artifacts they started as are retired). `/tools/images` is
the home page (`pages/ImageMakers.tsx`, one card per maker with an example in
`src/assets/image-makers/`); each maker is `/tools/images/<slug>` (`blog`, `events`, `build-mode`,
`customer-stories`), rendered by `pages/ImageMaker.tsx`. The makers are listed once, in
`src/image-maker/catalog.ts` (plain data: slug, names, card text, sizes, SEO title/headline/
description, the agent docs' one-line summary), which the home page and routes (`makers.ts`, adding
each maker's preview and lazy component), the page metadata (`seo.ts` `PAGES`) and the agent docs'
list of makers (`agent/markdown.ts` → `{{makers}}` in `agent/pages/tools/images.md`) all read. A maker is a folder,
`src/image-maker/makers/<engine>/`: `model.ts` (its saved document, `blank()`, sizes, colors),
`draw.ts` (pure canvas drawing of one document, used for the stage, the thumbnails and the PNG, so
they can't drift) and `<Name>Maker.tsx` (its settings panel). Everything else is the shared editor
in `src/image-maker/editor/`: `MakerFrame.tsx` (heading, the image list, Duplicate/Delete), `Share.tsx` (the Share button: one click copies the image's link, built from the document rather than the address bar so it's never an edit behind, and opens a panel with the link, what it carries, an uploads warning and the system share sheet),
`fields.tsx` (the settings controls), `PaintedCanvas.tsx` (a canvas that paints sharply at its
on-screen size and repaints when an image or font arrives), `HoggieGallery.tsx` (the hoggie picker
and its search ranking), `canvas.ts` (text measuring, the image cache, `requestFonts`) and
`download.ts`. Drawings use RoundHog as the site registers it (`@posthog/brand/fonts/css` in
`main.tsx`: SemiBold is weight 700, Bold 800 — the `SEMIBOLD`/`BOLD` constants), and
`requestFonts` loads the faces (and unicode-range subsets) a text needs, since canvas text doesn't
trigger web font loads. All four share one stylesheet, `src/image-maker/maker.css`, scoped to `.mk`
(`.mk-<engine>` for one maker's rules); buttons, segmented controls, inputs and the heading are the
site's own `.btn`, `.seg`, `.input` and `.page-header`, so restyle those in theme.css, not per
maker. The hoggies are
NOT a copy: `src/image-maker/hoggies.ts` builds every maker's list from the package
(`findAssets` + `getVariants`, tags plus the name, files at `/hoggies/<stem>.svg`), so a synced
hoggie shows up on the next deploy. The only hand-kept hoggie data is
`src/image-maker/data/hoggie-topics.json`, and it stays hand-kept on purpose: the Figma tags say
what a hoggie looks like, while topics tie PostHog subjects to it (`sql` → Desk Wizard, `pricing` →
Burning Money), and nothing in the package carries that. Without topics, far fewer real blog
titles match any hoggie. Keys are file stems (`climber-2`, as in `/hoggies/<stem>.svg`), values are
`|`-separated lowercase words or phrases, matched as whole words in the title and description (a
trailing `s` also matches). The blog maker's auto-match scores a topic 3 and a tag 1 and takes the
highest total. To change which hoggie a kind of post gets, edit this file; a key whose hoggie is
renamed or removed is ignored, so update it with the rename. The rest of a maker's data is `src/image-maker/data/<engine>.json` (logos,
customer logos and themes, build mode authors), pointing at same-origin files: the agent files
(`/logo/*.svg`) and `site/public/image-makers/` (Squeak Bold for event headlines, build mode logo,
paper rip and author photos, and the posthog.com/customers logos). `editor/store.ts`
(`useImageStore`) keeps a maker's images: this browser's localStorage (the list on the left, newest
40), saved a moment after each edit, and the address bar's `?image=` (base64url JSON, `link.ts`),
which always describes the image being edited, so the link is the save. Opening a link to an image
already in the list selects it rather than adding a copy. Uploads are object URLs kept in the
document for the session and dropped from links and storage (`withoutUploads`); downloads wait
for the drawing's images, then save through a plain `<a download>`. The blog maker also makes a new
image from `#new-<hex JSON>` (title, description, highlight, authors, hoggie, colors; documented
in `site/agent/pages/tools/images/blog.md`), which is how agents hand a v0 header to an author.
Every maker takes such a link: its `model.ts` `fromRequest` turns a plain JSON object of settings
into a document (shared helpers in `editor/request.ts`), `readLinkRequest` reads it from the hash,
and `useNewImageLinks` (`editor/store.ts`) adds it to the list. The same `fromRequest` backs the
`make_<maker>_image` WebMCP tools (`webmcp-tools.ts` schemas, whose value lists `tsc` checks
against each model's types; behavior in `src/image-maker/agent.ts`, lazy-loaded on the first call):
they draw the document with the maker's `draw.ts`, return a 960px JPEG preview as MCP `image`
content plus the `?image=` link, what the maker decided and `warnings`, and optionally `show` it
(`openInMaker` hands it to the maker's store, navigating there) or `download` it. The event tool also places a
hoggie the agent didn't place (`fit` in `agent.ts`): it moves it right, then shrinks it, until
drawing it changes no pixel in the date/time/location lines' boxes (`drawPost`'s `layout` out-param). Pictures an agent
passes (logos, photos) are URLs, not uploads, so links carry them; `loadedImage` loads cross-origin
ones in CORS mode so the canvas still exports (posthog.com's res.cloudinary.com images allow it).
To test the tools, Chrome needs `--enable-experimental-web-platform-features` for
`document.modelContext` (e.g. `agent-browser --args …`, then `agent-browser webmcp invoke`). On maker routes
the page panel is wider (`.page-wide`) and there is no footer, and from 901px wide the editor fills
the window instead of scrolling (`.app-fit` in theme.css, set by `Layout` for the catalog's maker
paths, min height 600px): the list and settings scroll inside it and the stage scales the image to
the room it has. At 900px and below the columns stack and the page scrolls. Settings run in the same order in every maker: what the image says (title or event details, then authors), its pictures (hoggie, your image, logos), colors, then fine-tuning (layout, headline style), and This image (Duplicate/Delete) last. Events: `image downloaded`, `image link copied` (`via`: the Share button or the panel's Copy), `image link shared` (system share sheet).
Run them locally with `pnpm dev:site` and open `/tools/images`.

To check a change to a maker's drawing, use the reference snapshots in `site/tests/makers/`
(README there): open a case's link, download it, and compare with
`node scripts/compare-png.ts <reference> <download>` (from `site/`). They show what the makers draw
now, not a spec, and CI doesn't check them: when a drawing changes on purpose, save the new download
over its reference (`--save`) in the same commit, and add or drop cases freely.

**Adding an image maker** (`<slug>` is its URL segment, `<engine>` its folder):

1. `src/image-maker/makers/<engine>/`: `model.ts` (the document type extending `Stamped`,
   `blank()`), `draw.ts` (draws one document; take images through `loadedImage` and list them in
   an `imagesOf` for downloads), and `<Name>Maker.tsx` (default export, built from `MakerFrame`,
   `ImageList`, `ImageActions`, `fields.tsx` and `useImageStore("<slug>", blank)`). Copy the
   closest existing maker; build mode is the smallest.
2. An entry in `src/image-maker/catalog.ts`. That alone adds its page metadata, prerendered page,
   sitemap entry and line in the agent docs.
3. Its preview and component in `src/image-maker/makers.ts` (`tsc` fails until both are there),
   with the preview image in `src/assets/image-makers/`.
4. Its agent doc, `site/agent/pages/tools/images/<slug>.md` (copy a sibling; the build fails
   without it).
5. Its styles, if any, in `src/image-maker/maker.css` under `.mk-<engine>`; most makers need only
   the shared rules (the stage sizing for a new aspect ratio, for one).
6. A case or two in `site/tests/makers/` (README), so the next change has something to compare.

**Analytics**: `initAnalytics` (`site/src/analytics.ts`) runs `posthog.init` once in `main.tsx`
before render (posthog.com's project; `person_profiles: "always"`; capturing opted out in dev) and
call sites use `posthog.capture` directly. It sets `capture_webmcp` — tools must register _after_
init, since posthog-js wraps
`registerTool` — and `opt_out_useragent_filter` so agent-driven browsers are kept (tagged
`$browser_type: "bot"`) rather than dropped; surveys/conversations/tours are off (they're
posthog.com's). Custom events: `asset copied`/`asset downloaded` (via `useAssetCopy`'s required
`asset` ref and `DownloadLinks`), `assets searched`, `crest tier toggled`,
`code copied` (`snippet` = the `slug` every `<CodeBlock>` must pass; the badges' are
`<badge-id>-html` and `<badge-id>-markdown`). Agents that fetch the static files directly (never running JS) aren't captured.
The build also writes `_headers` (markdown content type, CORS on the agent files, canonical
`Link` from each `.md` to its page, and for the hotlinked `/badges/*` a day of caching and
`Cross-Origin-Resource-Policy: cross-origin`).

There is **no `_redirects` file** (`_headers` is fine; it doesn't rewrite), and the old committed one was deleted: Pages serves
`dist/logo.html` at `/logo` and `dist/crests/marketing.html` at `/crests/marketing` by itself,
and every sitemap URL now has such a file. Rules would actively break it — `/logo /logo.html
200` makes Pages apply its own `.html` → extensionless 308 to the rewrite target and loop back
to `/logo` (this is what broke the first preview deploy), and a `/*  /index.html  200` SPA
fallback is followed whether or not an asset matches, so it shadows every prerendered file.
Anything genuinely unknown falls through to `404.html`, which Pages serves with a real 404
status (the SPA fallback used to answer 200) and which boots the app into its `*` route.
